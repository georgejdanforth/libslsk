# libslsk

libslsk is a Soulseek client protocol library in Zig. It has two public interfaces:

- A first-class Zig API that uses `std.Io`.
- A C library (static and shared) for use from other languages.

## Documentation

- [docs/SLSKPROTOCOL.md](docs/SLSKPROTOCOL.md): the protocol specification (a copy from Nicotine+). Read the relevant section before you implement or change a message. Do not edit this file.
- [docs/REFERENCES.md](docs/REFERENCES.md): other protocol references, reference implementations, and network rules.
- [docs/PLAN.md](docs/PLAN.md): the implementation plan.

Do not add or extend protocol messages that the specification does not document.

## Architecture

The library uses a sans-IO design. The protocol core does no I/O.

| Layer | Path | Responsibility |
|---|---|---|
| `slsk.proto` | `src/proto/` | Wire codecs. Pure encode and decode, no state. |
| `slsk.core` | `src/core/` | Protocol state machine. No `std.Io`, no clock, no sockets. |
| `slsk.Client` | `src/client/` | Zig driver. Takes `io: std.Io`, does all I/O, and runs the core. |
| C ABI | `src/c_api.zig`, `include/slsk.h` | Exports the core to C. |

Rules for the core:

- The host gives the core bytes, connection events, timer events, and the current time (`now_ms`). The core never reads a clock.
- The core returns actions (`open_conn`, `send`, `close`, `listen`, `transfer_ready`) and application events.
- The core exposes one timer deadline. The host calls `timerFired` at or after it.
- Connections are integer handles. The core assigns them.
- The core does not send file bodies. After the `F` handshake, it emits `transfer_ready`, and the host moves the bytes.
- The core takes an allocator at init. It does not use a global allocator.

Rules for the C ABI:

- C gets opaque handles only.
- Zig errors map to fixed `slsk_status` integers. Never reuse a number.
- Output types are `extern struct` and `extern union`. Convert Zig tagged unions at the boundary.
- The host pulls actions and events. The core never calls into foreign code.
- Buffers in output structs stay valid only until the next `slsk_core_*` call.
- `include/slsk.h` is written by hand. Keep the Zig `comptime` layout asserts and the C `_Static_assert` checks in sync.

A managed C client (with an internal `Io`) is out of scope for now.

## Commands

```sh
zig build                     # build the Zig module and the C libraries
zig build test                # unit tests and C tests
zig build test --fuzz         # unit tests with fuzz tests
zig build itest               # integration tests (needs SLSK_SOULFIND)
zig build install             # install libraries, header, and pkg-config file

scripts/soulfind.sh up        # start Soulfind in Docker on port 2242
scripts/soulfind.sh down      # stop Soulfind and delete its data
SLSK_SOULFIND=127.0.0.1:2242 zig build itest
```

If `SLSK_SOULFIND` is not set, `zig build itest` skips the integration tests.

## Testing

- Unit tests use `std.testing.allocator`, so each test also checks for memory leaks.
- Core tests use the `TestHost` helper. They are deterministic and use no sockets and no real clock.
- Codec tests use golden byte vectors and round trips. Unknown message codes decode to `.unknown`. They are not errors.
- Integration tests run against [Soulfind](https://github.com/soulfind-dev/soulfind) (`ghcr.io/soulfind-dev/soulfind`).

Soulfind facts for integration tests:

- A new username registers automatically on its first `Login`.
- Usernames must be printable ASCII. Use a random suffix, for example `itest-<random>`, to prevent `Relogged` conflicts.
- Search is a direct broadcast of `FileSearch` to all users, including the searcher. Searches arrive in batches, so wait with a timeout, not a fixed sleep.
- Soulfind has no distributed network. Use `tests/fake_server.zig` for distributed tests.
- Soulfind is GPL-3.0. Run it only as an external tool. Do not vendor or link it.

## Zig version and style

Use Zig 0.17.1. Before you write, review, or refactor Zig code, load these two skills:

- `zig-0-17`: API guidance for Zig 0.17. Many APIs changed in this release, for example `SafeAllocator` and the build system. Do not use the `zig-0.16` skill for this project.
- `zig-tiger-style`: TigerStyle coding rules. Follow them for assertions, naming, memory layout, and code structure.
